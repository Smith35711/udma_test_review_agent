# agent2 检视智能体 需求规格

- **版本**：v1.0（2026-09-15）
- **来源**：用户口述需求（`/home/gzq/langgraph/111`），经逐条确认后整理
- **范围**：仅覆盖口述稿明确提及的内容；未提及者一律不在本期范围内

## 1. 概述

- **定位**：面向 Linux C 代码的检视智能体，以 LangGraph 为运行框架，工程位于 `agent2/`。
- **输入与输出**：输入为命令行指定的待检视目录；输出为架构分析产物与按模块分隔的检视报告。
- **流程主体**：架构分析 → 代码检视；两阶段可由命令行选择单独或组合执行。
- **上下文前提**：生产环境模型上下文预算按 200K 计，模块规模策略据此划定。
- **基础设施**：模型调用（`llm.py::stream_llm_once`）、日志（`log.py`）、模型配置（`model_config.py`）已就绪，本文不重复定义。

## 2. 命令行接口

| 参数 | 含义 | 默认值 |
| --- | --- | --- |
| `--project DIR` | 待检视目录 | 必填 |
| `--stages LIST` | 执行阶段：`arch`（架构分析）、`review`（代码检视），可单选或组合 | `arch,review` |
| `--modules LIST` | 待检视模块编号，如 `M01,M03` | 全部模块 |
| `--concurrency N` | 并行数量；`1` 为串行，`N>1` 为并行上限 | `min(模块数, 4)` |
| `--timeout SEC` | 模型调用超时，同时作用于首 token 等待与 chunk 间隔 | 60 / 30 |
| `--log-level LEVEL` | 日志等级 | `INFO` |
| `--log-file PATH` | 日志文件路径 | `output/agent2.log` |

「分析可选项」由 `--stages` 承载：不含 `arch` 时跳过架构分析，直接复用既有产物进入检视。

## 3. 启动前置检查

1. 校验命令行参数合法性。
2. **模型连通性测试**：以当前生效模型发起一次最小调用；不通过则报错返回异常（退出码非 0），通过则继续。

## 4. 阶段一：架构分析（arch）

### 4.1 模块扫描分析（确定性）

对指定目录进行分析，产出四项：

1. **模块划分**：按 `.c` 与 `.h` 配对，一个模块对应一组 `.c` / `.h` 文件。
2. **规模统计**：逐模块统计代码行数（`.c` 与 `.h` 之和）、字符数、预估 Token 值；Token 采用本地简单计算，不调用模型，精度以量级正确为准。
3. **模块编号**：按模块路径字典序分配 `M01`、`M02`……
4. **产物落盘**：全部模块汇为一份总表，以 JSON 写至 `output/references/`。

### 4.2 模块间依赖（背景信息）

在模块清单基础上，整理出每个模块**用到的、定义在项目其他模块中**的符号：宏（含宏函数）、
函数的完整签名、结构体与类型定义。只收项目内部依赖，标准库与系统调用一概不收。

产物写入 `output/references/dependencies.json`，并作为检视阶段的「背景信息」注入上下文。

### 4.3 其他分析节点

本阶段后续将补充其他分析节点，本期留空，等待具体要求。

## 5. 阶段二：代码检视（review）

### 5.1 前置校验

检视以架构分析产出的模块清单为依据。清单不存在或无可检视模块编号时，直接报错退出并打印提示。

### 5.2 规模分支

| 判定条件 | 分支 |
| --- | --- |
| ≤ 2000 行 | 小模块 |
| > 2000 行 | 大模块 |

行数口径为 `.c` 与 `.h` 之和。

大模块走**先分解、再逐块检视**的路径：确定性节点先产出精简符号表（对外接口、内部函数、
全局变量）与函数调用图，交由大模型判断模块形态并给出逻辑子块的划分；划分由确定性节点
校验（每个函数恰好归属一块、每块不超阈值、循环调用组不被拆散）后才并行检视各子块，
结果合并为一份模块报告。分解只涉及逻辑子块，不修改被测项目的物理文件。

### 5.3 小模块检视

1. 全量读取该模块源码及背景信息。
2. 以指定字段的 JSON 结构化输出（经 schema 校验）。
3. 落盘保存。

### 5.4 格式校验（确定性）

- 仅校验 JSON 格式正确性，不校验内容。
- 不通过：**当前模块直接终止**，不再进入反驳与报告环节。
- 该模块失败不影响串行或并行的后续流程，其余模块照常执行；失败须报错并记入日志。

### 5.5 反驳

对上一环节产出的全部检视意见逐条反驳，结论取三态之一：**维持**（confirmed）、**反驳**（refuted）、**待确认**（uncertain）。

- 维持与反驳均须给出充足的证据链与上下文。
- 反驳过程**不得增加或减少** findings 条目，仅改变其结论。

### 5.6 遗漏补做（确定性节点 + 反驳节点）

确定性节点检查是否存在未经充分反驳的 finding；若有，将该检视意见重新交回反驳节点补做结论，并合并入产物落盘。

### 5.7 报告生成

1. 确定性节点将经反驳的产物格式化为 Markdown 文档。
2. 在文档开头生成总结摘要。**摘要由产物统计确定性地算出，不调用模型**——它只是把已有的条数与等级分布摆到开头，用模型写多一次调用，也多一条会让整个模块拿不出结果的失败路径。
3. 落盘至该模块子目录。

## 6. 执行模式

- **单模块串行循环**：按模块清单顺序逐个执行完整检视流程。
- **多模块并行**：并发数由 `--concurrency` 指定，`1` 即串行。

## 7. 产物目录约定

```
output/
├── references/        架构分析产物（模块清单总表等）
├── M01/               模块 M01 的检视中间产物与最终产物
└── ...
```

每个模块的中间产物与最终产物必须全部落在该模块子目录内，不得遗漏或外溢。
